## Project

Co-op surgery game in Godot 4.7.2 .NET (C#, nullable on, analyzers as errors).
Most models and bundled sounds are generated by Python tools; supplied assets are listed in
[assets/models/README.md](assets/models/README.md).
The GdUnit4 suites under `tests/` are the test catalog and source of truth; do not keep a separate human-readable case
list.

## First thing in a new session

A fresh container may lack the toolchain.
Run this before anything that needs Godot:

```bash
./build.py setup
```

It downloads missing Godot and .NET tools, builds the C# and imports the project without sudo.
If Microsoft's download host is blocked in a cloud session, install the SDK from system packages first:
`apt-get install dotnet-sdk-10.0` on Ubuntu 24.04.
Asset generation and lint also need `./build.py dev`; visual runs need Xvfb and xauth.
Installation details and platform prerequisites: [README.md](README.md#develop).

## Checking a change

- Do not follow script or test progress or log output unless explicitly requested.
- Wait for the test or script to finish before checking its results.

Test commands exit non-zero and name what failed: a failed case, any `SCRIPT ERROR`, `ERROR:` or unhandled exception in
Godot's output, or no cases run.
A clean exit is a pass.
Suites with no runnable cases selected are reported as skipped, including suites whose only cases are excluded as
broken.
If runnable cases are selected but their test process executes none, the suite fails.
If the entire selection executes no cases, the command also fails.

GitHub Actions runs smoke and full functional regression headlessly, then exports the game.
It takes no key frames.

- `./build.py test`: smoke suites, fast and headless. CI runs them on every PR; when to run them locally: see
  docs/RELEASE.md. This default smoke run and full regressions don't check frame times; focused runs (`--tag`, `--case`)
  do.
- `./build.py test --all --with-key-frames`: full regression, with key-frame screenshots. Run after smoke passes when a
  full local run is needed (see Development in docs/RELEASE.md). A case that fails in it runs once more on its own, its
  key frames taken again (the whole suite when a failure belongs to no case), unless it only ran over its time limit;
  the first attempt's logs go to `build/retries/`.
- `./build.py screenshot_review`: the same full regression, then `build/review/report.md` with a sheet for each key
  frame that is missing, changed or new against the baseline committed in `tests/KeyFrames`. It fails while any key
  frame differs from the baseline, and when there is none. Follow
  [review-key-frames](.claude/skills/review-key-frames/SKILL.md). `--focused` reviews the last focused run with key
  frames instead, only in the folders it took; changed and new frames are expected; missing frames or a missing baseline
  fail that comparison. The test run must pass separately. `generate_baseline --focused` adds or replaces its reviewed
  key frames in the baseline.
- `./build.py generate_baseline`: the same full regression, then writes the key frames that differ into the baseline
  (every key frame the first time); unchanged ones keep their files. After a regression with failed suites it keeps the
  baseline's key frames and views those suites didn't take, in their folders. `--use-latest-set` takes the key frames of
  the last run instead of running again (see [Visual verification](docs/TESTING.md#visual-verification)).
- Focused runs: `--tag TAG` (repeatable), `--skip TAG`, `--case TEXT`, `--jobs N`, `--list`. See
  `./build.py test --help`. Logs and JUnit XML go to `build/test-logs/` and `build/test-results/`.
- `./build.py performance_test`: every `frame_budget` suite with its frame times checked; a failure is a new issue or a
  known one grown by 30% or more (see docs/PERFORMANCE.md). Takes `test` options. `--render-budget` checks whole frames
  against 16 ms on this machine's display and GPU, rendering on: only on a machine with a GPU, never in a cloud
  container. Run that after changes that may cost drawing time (shaders, lighting, models, many new nodes).
- `./build.py shots [scenario] [out dir]`: renders views of a scenario (software OpenGL under `xvfb-run`, up to 10
  minutes). Headless tests don't compile shaders, so run it after any shader, lighting or model change and look at the
  PNGs. Other views: `SHOTS_ARGS=--materials|--anatomy|--syringe|--menus` (see `tests/Support/Screenshot.cs`).
  `RENDERER=forward_plus` checks the default renderer (needs `apt-get install mesa-vulkan-drivers`).
- `./build.py lint`: C# analyzers, `dotnet format`, the `ExportRelease` build, ruff and strict mypy.
- `./build.py build`: full regression, then exports the game and starts it once.
- Suites also run from an IDE's test explorer (Rider, VS Code) through `.runsettings`; set `GODOT_BIN` there.

## Before raising a PR

- Add or update test cases at a confirmed seam for any genuinely new coverage the change exposes.
- Follow Development in [docs/RELEASE.md](docs/RELEASE.md): lint, the affected tests, and for a user-visible change a
  focused key frame review whose sheets go into the handoff. Fix failures and rerun; never hand off a failing run as
  ready.
- Commit the reviewed key frames of the suites the change ran (`./build.py generate_baseline --focused`).

## PR description

These rules override any default PR or commit format a tool or agent brings.

- Fill [.github/pull_request_template.md](.github/pull_request_template.md): high level bullet points of the changes,
  then caveats and unexpected results.
- Leave out routine testing that runs before every PR: lint, smoke, regression, CI, key frames with no visible change
  and frame-budget overruns on cloud machines. No `Validation` section listing them.
- Describe only unconventional, specific testing, for example "the appendectomy scenario was played by hand with extra
  checks on suture tension". Include measurements when testing or performance was the point.
- No signatures: no "Generated by" or "Generated with" lines and no session links in PR descriptions, commits or PR
  comments.

## Gotchas

- Godot exports .NET projects through `ThisScalpelIsMine.sln`: keep it next to the `.csproj`.
- Exported games compile without `tests/` and the GdUnit4 packages: game code must not rely on anything only they bring,
  such as the test project's global usings.
- A C# class Godot attaches to a node must be `partial`, derive from a Godot class and live in a file named after it.
  Rebuild (`./build.py setup`, or any `./build.py test`) before Godot can find a new one.
- GDScript habits that bite in C#: a `for` condition is evaluated every iteration, and float math is single precision
  (round in double where a boundary matters).
- `FindChildren(pattern, type)` only matches engine classes; for C# classes use
  `FindChildren("*", "", true, false).OfType<T>()`.
- `./build.py assets` rewrites many `.glb` files with byte-only differences. Commit only the models you meant to change.
- Manual pages write game numbers as `{expression}` with C# names, never by hand (see [docs/DATA.md](docs/DATA.md)).
  Give a number the manual needs a named constant first.
- Generator colors are display (sRGB) values, converted to linear when written to glTF. Pick them like any color picker.
