# This Scalpel Is Mine

Co-op surgery game in Godot 4.7.2 .NET (C#, nullable on, analyzers as errors). Models and sounds are generated by
Python tools. Architecture, data formats and mechanics: [docs/DESIGN.md](docs/DESIGN.md). The GdUnit4 suites under
`tests/` are the test catalog.

## First thing in a new session

Nothing is installed in a fresh container. Run this before anything that needs Godot:

```bash
./build.py setup
```

It downloads Godot .NET into `.tools/` (and the .NET 10 SDK into `.tools/dotnet` when the system has none), builds
the C# and imports the project. No sudo, a few minutes. Where Microsoft's download host is blocked, install the SDK
from the system packages first (`apt-get install dotnet-sdk-10.0` on Ubuntu 24.04). Asset generators additionally need `./build.py dev` (Python 3.11
venv with Blender as a module, about 400 MB).

## Checking a change

- GdUnit4 suites are the source of truth. Do not maintain a separate human-readable case catalog.
- `./build.py test`: fast, headless suites in the `smoke` category. Run this first.
- `./build.py test --all --with-key-frames`: full regression with key-frame screenshots. Run only after smoke passes.
- `./build.py test --tag TAG` (repeatable, suites with all of them), `--skip TAG` and `./build.py test --case TEXT`
  (test cases whose name, arguments included, contains TEXT): focused validation by feature or case.
  `--with-key-frames` makes `visual_confirmation` suites save their key frames (under `xvfb-run` with the compatibility
  renderer) and check the frame budget; without it they run headless and skip them. `--jobs N` runs N suites at once
  (with key frames, `visual_confirmation` suites still run alone, after the others, so their frame times aren't slowed
  by their neighbours). `--ci-run` reports frame times without checking them (CI machines are slower). `--list` shows
  what would run.
- A suite fails on a GdUnit failure, no cases run, or any `SCRIPT ERROR`, `ERROR:` or unhandled exception in its log.
  Test logs and JUnit XML results go to `build/test-logs/` and `build/test-results/`.
- The suites also run from an IDE's test explorer (Rider, VS Code) through `.runsettings`; set `GODOT_BIN` there.
- `./build.py shots [scenario] [out dir]`: renders views of a scenario through `xvfb-run` with the compatibility
  renderer (software OpenGL, no GPU needed). Look at the PNGs for anything visual: shaders, lighting, models.
  Rendering is slow here, allow up to 10 minutes.
- `RENDERER=forward_plus ./build.py shots` checks the default renderer. It needs software Vulkan: `apt-get install mesa-vulkan-drivers`.
  `SHOTS_ARGS=--materials ./build.py shots` renders the material board (families and skin tones) and both hands in every
  grip. Other views: `--anatomy`, `--syringe`, `--menus` (see `tests/Support/Screenshot.cs`).
- Shader errors only show up when something is rendered: headless tests don't compile shaders, screenshots do.
- `./build.py lint`: C# analyzers and `dotnet format`, ruff and strict mypy on the Python tools.

## Before raising a PR

- Review the test cases and add or update any genuinely unique coverage exposed by the change.
- Run the `smoke` category for quick validation.
- Only after smoke passes, run the full regression.
- The full regression must be green before raising a PR. Fix failures and rerun the checks; do not hand off a failing regression as ready.
- Review every deliberate key-frame screenshot and validate visual cohesiveness, continuity, lack of glitching,
  clipping and visual artifacts.

## Test structure and policy

- Suites are separated into folders by feature (`tests/<Feature>/<Name>Test.cs`, namespace `Scalpel.Tests.<Feature>`)
  and use GdUnit4Net as the runner and assertion framework: `[TestSuite, RequireGodotRuntime]` on the class,
  `[TestCase]` on each case. Categories are not folders. Shared helpers that aren't tests live in `tests/Support/`.
- A list of cases that differ only in a value (every scenario) is one method with a `[TestCase(value)]` row per value.
- Each suite declares its categories as `[TestCategory("...")]` attributes. A suite that needs Godot options declares
  them the same way, e.g. `[GodotArgs("--fixed-fps", "60")]` to run long surgeries faster than real time, and
  `[IsolateCases]` gives every case a Godot process of its own.
- Run independent suites in parallel where possible.
- A test must do what its name and messages claim. A case that says a scenario is completed plays it through like a
  player and passes only on the game's own success report, not on state the test set itself, a shortened run or a
  loosened threshold. If the claimed behavior can't be reached, the case fails or is known-broken (below); it never
  passes by checking something easier.
- Keep runs short by not checking the same thing twice. A mechanic an end-to-end case in the same run already proves
  needs no dedicated check, and a sweep over every scenario runs the checks that don't depend on the scenario once.
  CI runs `smoke` first and the full run skips it. A case with key frames is one case: it takes them only in a run
  with `--with-key-frames` (`KeyFrames.Wanted()` in `tests/Support/KeyFrames.cs`), never a copy for screenshots.
- Prefer comprehensive end-to-end feature checks. For example: the surgeon picks a scalpel up from the table,
  walks to the patient, makes a light 5 cm cut, and the resulting opening measures 5 cm.
- Categorize conservatively. A category must describe either the test type or a feature selection worth rerunning,
  such as all scalpel tests. Categories in use: `smoke`, `slow`, `scenario`, `network`, `tissue_modification`,
  `liquids`, `tool_<id>`, `tool_all`, `visual_confirmation` and `broken`. `slow` means one test takes longer than half
  the per-test limit (`TEST_TIMEOUT` in `build.py`, 60 s); its cases then take `[TestCase(Timeout = Limits.Slow)]`. A
  test that runs longer than its limit is stopped and fails, named in its log.
- Keep simulated player actions and direct state changes apart. `Player*` steps in `tests/Support/SurgeryDriver*.cs`
  (`PlayerRequestsItem("scalpel")`, `PlayerCutsSkin(from, to, level)`) walk, hold tools and press the controls a
  player has, so the game itself does the work. Methods in `tests/Support/SurgeryState.cs` are named for the state
  they write directly (`SkinIsCut(...)`, `PatientIsAsleep(...)`) and only set up what a test isn't about.
  Add reusable steps there rather than poking game state from a test. Game members a test needs are `internal`
  (the tests build into the game's assembly), never public for the test's sake.
- Simulated player input goes through the engine's input, as a player's does: `tests/Support/PlayerInput.cs` sends
  actions, keys and mouse motion with `Input.ParseInputEvent()`. Never call an input handler (`_UnhandledInput()`,
  `SteerHand()`, `AimTool()`) or set what it would set from a test: called directly, a press lands at another point
  of the frame than a player's, and a test can pass where the game fails. Sent input reaches the game with the next
  frame, so wait a frame before checking what it did.
- Use hard programmatic checks for measurable defects including geometry, gaps, alignment and physics calculations.
- Deliberately capture screenshots from the test immediately after named actions; never use elapsed time alone to
  decide when a screenshot is taken.
- If an end-to-end test already captures a feature's visual confirmation, more granular tests for that feature do
  not need duplicate screenshots.
- `smoke` tests are headless, programmatic, and each takes less than five minutes. A smoke case may also take key
  frames in a run with them, only when its assertions fully validate the behavior without the screenshots.
- If a non-trivial failure cannot be fixed in the current change, move its case to a method of its own marked
  `[TestCategory("broken")]` with `[TestCase(..., Description = "BROKEN: reason")]` (GdUnit's own ignore doesn't work
  with the test adapter). `build.py` lists such cases as pending instead of running them; with `RUN_BROKEN=1` they run
  and fail. Disable any main-menu scenario that relies on it (`disabled=true` in its cfg) and place a comment beside
  the disablement naming the broken case. Never silently delete or weaken the case.

## Visual verification policy

- Every user-visible feature or visual change must add or update a deterministic visual test.
- Capture the untouched state, the key interaction frame and the persistent result. Spatial or layered changes also
  require an oblique close-up that exposes depth and intersections.
- Inspect continuity, clipping, mesh intersections, material consistency, tool contact, animation transitions and UI
  legibility. Use programmatic geometry, mask, depth, normal, contour and gap checks wherever a defect is measurable.
- Perceptual screenshot comparisons may flag regressions, but they do not replace human or vision-agent review for
  overall cohesiveness. Report reviewed screenshot paths in the handoff.

## Frame-time budget

- Interactive gameplay must stay within a 16 ms worst-frame CPU budget so 60 fps remains possible.
- Measure the elapsed time of the game work being changed; do not use displayed FPS as the acceptance metric because
  VSync, compositor refresh and test-host presentation can cap it independently of game performance.
- Visual tests that exercise dynamic work must report the worst measured frame time and fail when it exceeds 16 ms.
  The check runs locally only: CI passes `--ci-run`, which reports the frame times without failing on them.
  `tests/Support/FrameBudget.cs` measures the wall time between frames under `--fixed-fps` with rendering off between
  key frames, and names what the test was doing during the slowest one.
  Check it with `Budget.Check(withKeyFrames)` (the driver's `Budget` or your own), never with a timer around one
  function: the budget is for the whole frame.
  A case known to go over that can't be fixed in the current change passes the reason as `broken`: it then prints a
  `BROKEN:` line instead of failing, and its other checks still run.
- The reference machine is an i9-14900HX. .NET sizes its young generation by the CPU's L3 cache, so `build.py test` runs
  with the reference machine's (`DOTNET_GCgen0size`). .NET reads that setting only from the environment, not from the
  game's runtime config, so players get their own CPU's size.
- The game keeps collections short for players too: gen2 collections run in the background
  (`GCLatencyMode.SustainedLowLatency`), and a full collection runs as a surgery starts, before play.
- Known issue: the .NET runtime's own stalls (a garbage collection now and then, compiling code on first use) can take
  a frame over. The check measures them: a frame over only because of them prints a `BROKEN:` line
  (`FrameBudget.RuntimeStalls`), unless one stall took longer than `FrameBudget.StallLimit`; a frame whose own work is
  over still fails.

## Gotchas

- A C# class Godot attaches to a node must be `partial`, derive from a Godot class and live in a file named after it.
  After adding one, rebuild (`./build.py setup`, or any `./build.py test`) before Godot can find it.
- GDScript habits that bite in C#: a `for` condition is evaluated every iteration (GDScript's `for i in n` evaluates
  `n` once), and float math is single precision where GDScript's was double (round in double where a boundary
  matters).
- `FindChildren(pattern, type)` only matches engine classes; for C# classes use
  `FindChildren("*", "", true, false).OfType<T>()`.
- `./build.py assets` rewrites many `.glb` files with byte-only differences. Commit only the models you meant to change.
- Manual pages write game numbers as `{expression}` with C# names (`{Patient.HighPressure}`,
  `{drug.diazepam.Dose}`), never by hand. Give a number the manual needs a named constant first.
- Generator colors are display (sRGB) values, converted to linear when written to glTF. Pick them like any color picker.
