# This Scalpel Is Mine

Co-op surgery game in Godot 4.7.2 (GDScript, typed). Models and sounds are generated by Python tools.
Architecture, data formats and mechanics: [docs/DESIGN.md](docs/DESIGN.md). GUT scripts under `tests/` are the test catalog.

## First thing in a new session

Nothing is installed in a fresh container. Clone with `--recurse-submodules`, or run this before anything that needs
Godot (it initializes the pinned GUT submodule automatically):

```bash
./build.sh setup
```

It downloads Godot into `.tools/` (retrying failed downloads) and imports the project. No sudo, about a minute.
Asset generators additionally need `./build.sh dev` (Python 3.11 venv with Blender as a module, about 400 MB).

## Checking a change

- GUT test scripts are the source of truth. Do not maintain a separate human-readable case catalog.
- `./build.sh test`: fast, headless tests tagged `smoke`. Run this first.
- `./build.sh test --all`: full GUT regression. Run only after smoke passes.
- `./build.sh test --tag TAG` and `./build.sh test --case TEXT`: focused validation by feature or case.
- Test logs and JUnit XML results go to `build/test-logs/` and `build/test-results/`.
- `./build.sh shots [scenario] [out dir]`: renders views of a scenario through `xvfb-run` with the compatibility
  renderer (software OpenGL, no GPU needed). Look at the PNGs for anything visual: shaders, lighting, models.
  Rendering is slow here, allow up to 10 minutes.
- `RENDERER=forward_plus ./build.sh shots` checks the default renderer. It needs software Vulkan: `apt-get install mesa-vulkan-drivers`.
  `SHOTS_ARGS=--materials ./build.sh shots` renders the material board (families and skin tones) and both hands in every grip.
- Shader errors only show up when something is rendered: headless tests don't compile shaders, screenshots do.
- `./build.sh lint`: ruff and strict mypy on the Python tools.

## Before raising a PR

- Review the GUT cases and add or update any genuinely unique coverage exposed by the change.
- Run the `smoke` tag for quick validation.
- Only after smoke passes, run the full regression.
- Review every deliberate key-frame screenshot and validate visual cohesiveness, continuity, lack of glitching,
  clipping and visual artifacts.

## Test structure and policy

- Tests are separated into folders by feature and use GUT as the runner and assertion framework.
- Run independent test scripts in parallel where possible.
- Prefer comprehensive end-to-end feature checks. For example: the surgeon picks a scalpel up from the table,
  walks to the patient, makes a light 5 cm cut, and the resulting opening measures 5 cm.
- Tag conservatively. A tag must describe either the test type or a feature selection worth rerunning, such as all
  scalpel tests. Starter tags are `smoke`, `slow`, `tussue_modification`, `liquids`, `tool_<id>` and
  `visual_confirmation`. `slow` means one test takes longer than five minutes.
- Define descriptive reusable steps and assertions, such as `player_requests_item("scalpel")` and
  `player_is_unconscious()`.
- Use hard programmatic checks for measurable defects including geometry, gaps, alignment and physics calculations.
- Deliberately capture screenshots from the test immediately after named actions; never use elapsed time alone to
  decide when a screenshot is taken.
- If an end-to-end test already captures a feature's visual confirmation, more granular tests for that feature do
  not need duplicate screenshots.
- `smoke` tests are headless, programmatic, contain no visual confirmation, and each takes less than five minutes.
  A fast visual-derived case may be reused as smoke only when its assertions fully validate the behavior without
  requiring the screenshot.
- If a non-trivial failure cannot be fixed in the current change, mark its GUT case pending with a `BROKEN:` reason.
  Disable any main-menu scenario that relies on it and place a code comment beside the disablement naming the broken
  GUT test. Never silently delete or weaken the case.

## Visual verification policy

- Every user-visible feature or visual change must add or update a deterministic visual test.
- Capture the untouched state, the key interaction frame and the persistent result. Spatial or layered changes also
  require an oblique close-up that exposes depth and intersections.
- Inspect continuity, clipping, mesh intersections, material consistency, tool contact, animation transitions and UI
  legibility. Use programmatic geometry, mask, depth, normal, contour and gap checks wherever a defect is measurable.
- Perceptual screenshot comparisons may flag regressions, but they do not replace human or vision-agent review for
  overall cohesiveness. Report reviewed screenshot paths in the handoff.

## Frame-time budget

- Interactive gameplay must stay within a 16 ms worst-frame CPU budget so 60 fps remains possible.
- Measure the elapsed time of the game work being changed; do not use displayed FPS as the acceptance metric because
  VSync, compositor refresh and test-host presentation can cap it independently of game performance.
- Visual tests that exercise dynamic work must report the worst measured frame time and fail when it exceeds 16 ms.

## Gotchas

- After adding a script with a new `class_name`, run `./build.sh setup` (it re-imports) or the class isn't found.
- `./build.sh assets` rewrites many `.glb` files with byte-only differences. Commit only the models you meant to change.
- Generator colors are display (sRGB) values, converted to linear when written to glTF. Pick them like any color picker.
