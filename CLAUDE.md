# This Scalpel Is Mine

Co-op surgery game in Godot 4.7.2 .NET (C#, nullable on, analyzers as errors). Models and sounds are generated by
Python tools. Architecture, data formats and mechanics: [docs/DESIGN.md](docs/DESIGN.md). The GdUnit4 suites under
`tests/` are the test catalog and the source of truth; do not keep a separate human-readable case list.

## First thing in a new session

Nothing is installed in a fresh container. Run this before anything that needs Godot:

```bash
./build.py setup
```

It downloads Godot .NET into `.tools/` (and the .NET 10 SDK into `.tools/dotnet` when the system has none), builds
the C# and imports the project. No sudo, a few minutes. Where Microsoft's download host is blocked, install the SDK
from the system packages first (`apt-get install dotnet-sdk-10.0` on Ubuntu 24.04).
Asset generators additionally need `./build.py dev` (Python 3.11 venv with Blender as a module, about 400 MB).
Dev setup also provisions Xvfb and xauth for visual tests: on Fedora it extracts the packages into `.tools/xvfb`
without sudo. Every build command automatically uses that local installation. Elsewhere install `xvfb` and `xauth`
with the system package manager before dev setup.

## Checking a change

Every command below exits non-zero and names what failed: a failed case, any `SCRIPT ERROR`, `ERROR:` or unhandled
exception in Godot's output, or no cases run. A clean exit is a pass.
Suites with no runnable cases selected are reported as skipped, including suites whose only cases are excluded as broken.
If runnable cases are selected but their test process executes none, the suite fails. If the entire selection executes
no cases, the command also fails.

GitHub Actions runs smoke and full functional regression headlessly, then exports the game. It takes no key frames.

- `./build.py test`: smoke suites, fast and headless. Run this first.
- `./build.py test --all --with-key-frames`: full regression, with key-frame screenshots and the frame budget. Run
  only after smoke passes. A case that fails in it runs once more on its own, its key frames taken again (the whole
  suite when a failure belongs to no case); the first attempt's logs go to `build/retries/`.
- `./build.py screenshot_review`: the same full regression, then `build/review/report.md` with a sheet for each key
  frame that is missing, changed or new against the baseline committed in `tests/KeyFrames`. It fails while any
  key frame differs from the baseline, and when there is none. Follow the `review-key-frames` skill.
- `./build.py generate_baseline`: the same full regression, then writes the key frames that differ into the baseline
  (every key frame the first time); unchanged ones keep their files. After a regression with failed suites it keeps
  the baseline's key frames and views those suites didn't take, in their folders. `--use-latest-set` takes the key
  frames of the last run instead of running again (see Visual verification).
- Focused runs: `--tag TAG` (repeatable), `--skip TAG`, `--case TEXT`, `--jobs N`, `--list`. See
  `./build.py test --help`. Logs and JUnit XML go to `build/test-logs/` and `build/test-results/`.
- `./build.py full_performance_run`: the full regression on this machine's display and GPU, rendering on, checking
  whole frames against 16 ms. Only on a machine with a GPU, never in a cloud container; it takes no key frames. Run it
  after changes that may cost drawing time (shaders, lighting, models, many new nodes).
- `./build.py shots [scenario] [out dir]`: renders views of a scenario (software OpenGL under `xvfb-run`, up to 10
  minutes). Headless tests don't compile shaders, so run it after any shader, lighting or model change and look at
  the PNGs. Other views: `SHOTS_ARGS=--materials|--anatomy|--syringe|--menus` (see `tests/Support/Screenshot.cs`).
  `RENDERER=forward_plus` checks the default renderer (needs `apt-get install mesa-vulkan-drivers`).
- `./build.py lint`: C# analyzers, `dotnet format`, the `ExportRelease` build, ruff and strict mypy.
- `./build.py build`: full regression, then exports the game and starts it once.
- Suites also run from an IDE's test explorer (Rider, VS Code) through `.runsettings`; set `GODOT_BIN` there.

## Before raising a PR

- Add or update test cases for any genuinely new coverage the change exposes.
- `./build.py lint`, then `./build.py test`, then `./build.py screenshot_review` must all pass. Fix failures and
  rerun; never hand off a failing run as ready.
- Review the key frames the change affects through `build/review/report.md` (see Visual verification) and list the
  reviewed sheets in the handoff.
- When the review lists key frames that are missing, changed or new and every sheet looks right, run
  `./build.py generate_baseline --use-latest-set` and commit `tests/KeyFrames` with the change. The review then passes.

## Test structure and policy

- Suites live in `tests/<Feature>/<Name>Test.cs` (namespace `Scalpel.Tests.<Feature>`), with
  `[TestSuite, RequireGodotRuntime]` on the class and `[TestCase]` on each case. Shared helpers live in
  `tests/Support/`.
- Compatible cases share setup through `SharedScene<T>` (`tests/Support/SharedScene.cs`): use a named group, reset
  its input and temporary tools before each case, and complete it only after all assertions pass. Run
  `DiscardIncomplete()` after each case and `Stop()` after the suite. Empty groups get fresh scenes. Keep cases that
  change tissue, IV delivery, sedation or animation baselines isolated unless their reset is explicitly verified.
  Keep individual cases and their result timings; do not replace them with one opaque loop.
- Ordinary driver cases advance only the nurse delivery/cooldown clock through `SurgeryState`; they do not wait for
  ordering delays. `NurseShopTest` alone enables `WaitForNurse` and checks delivery timing, deadline expiration and
  cooldown rejection. General case/session safety timeouts remain enabled. Fixtures that need anesthesia before
  tissue changes assert that preparation explicitly rather than relying on time spent waiting for the nurse.
- Core mechanic assertions belong in a fitting full scenario flow when that flow already performs the action.
  Specialized failure paths and destructive stress checks stay separate. Shared flow checks live in `tests/Support/`.
- Cases that differ only in a value (every scenario) are one method with a `[TestCase(value)]` row per value.
- A suite declares its categories with `[TestCategory("...")]` and its Godot options with
  `[GodotArgs("--fixed-fps", "60")]`; `[IsolateCases]` gives every case its own Godot process.
- Categories describe the test type or a feature worth rerunning: `smoke`, `slow`, `scenario`, `network`,
  `tissue_modification`, `liquids`, `tool_<id>`, `tool_all`, `visual_confirmation`, `broken`. `slow` means one case
  takes over half the per-test limit (`TEST_TIMEOUT` in `build.py`); its cases take
  `[TestCase(Timeout = Limits.Slow)]`.
- `smoke` cases are headless and programmatic, each under five minutes. They may take key frames only when their
  assertions fully validate the behavior without them.
- A test does what its name and messages claim. A case that says a scenario is completed plays it like a player and
  passes only on the game's own success report, never on state the test set, a shortened run or a loosened threshold.
  If the claim can't be reached, the case fails, or is a known issue or broken (below).
- Prefer comprehensive end-to-end checks: the surgeon picks a scalpel up from the table, walks to the patient, makes a
  light 5 cm cut, and the opening measures 5 cm.
- Don't check the same thing twice. A mechanic an end-to-end case already proves needs no dedicated check; a sweep
  over every scenario runs scenario-independent checks once.
- Choose one representative per behavior class, plus values just inside, at and beyond a meaningful boundary.
  Repeated input is justified by cumulative behavior or an animation transition; avoid replaying equivalent strokes
  or repositioning when the target has not changed.
- Use hard programmatic checks (geometry, gaps, alignment, masks, depth, physics) wherever a defect is measurable.
- Player actions and direct state changes stay apart. `Player*` steps in `tests/Support/SurgeryDriver*.cs`
  (`PlayerRequestsItem("scalpel")`, `PlayerCutsSkin(from, to, level)`) walk, hold tools and press the player's
  controls. `tests/Support/SurgeryState.cs` methods are named for the state they write (`SkinIsCut(...)`,
  `PatientIsAsleep(...)`) and only set up what a test isn't about. Add reusable steps there.
- Simulated input goes through `tests/Support/PlayerInput.cs` (`Input.ParseInputEvent()`). Never call an input
  handler (`_UnhandledInput()`, `SteerHand()`, `AimTool()`) or set what it would set. Sent input arrives with the next
  frame: wait a frame before checking it.
- Game members a test needs are `internal` (the tests build into the game's assembly), never public for a test.
- Known issue: if a non-trivial failure can't be fixed in the current change and fails the same way every run, wrap
  the case in `KnownIssue.Expect(failure, ...)` (`tests/Support/KnownIssue.cs`) with
  `[TestCase(..., Description = "KNOWN ISSUE: reason")]`. It runs with the rest of the regression and passes only when
  it fails with a message containing `failure`: pick the part that says where it breaks (the objective that doesn't
  complete), so everything before it is still checked. Another failure fails it as usual, and once it passes it fails
  until it's made an ordinary case again.
- Broken: a failure that can't be pinned that way (it passes or fails from run to run, or shows only in a key frame
  review) moves its case to its own method with `[TestCategory("broken")]` and
  `[TestCase(..., Description = "BROKEN: reason")]` (GdUnit's own ignore doesn't work with the adapter). It's skipped:
  `build.py` lists it as pending, and `RUN_BROKEN=1` runs it.
- Disable any scenario that relies on a known issue or a broken case (`disabled=true` in its cfg, with a comment
  naming the case). Never delete or weaken the case.

## Visual verification

- Every user-visible change adds or updates a deterministic visual test. It captures the untouched state, the key
  interaction and the persistent result, plus an oblique close-up for spatial or layered changes.
- Capture with `KeyFrames` right after a named action, never on elapsed time. A case with key frames is one case:
  it takes them only when `KeyFrames.Wanted()`, never in a copy made for screenshots. A feature an end-to-end case
  already captures needs no more screenshots.
- Capture each distinct visual claim once. Shared helpers opt into stitch/staple progress shots; callers capture
  their final result. Keep one untouched reference per distinct fixture, and use the player view for HUD, zoom and
  transparency claims instead of adding site views that cannot show them. Internal objective flags use assertions.
- Every key frame carries a description of what it should show (`Capture("on_hook", "the card on its hook, ...")`):
  the review prints it beside the sheet. Write what a reviewer checks the picture against, not the action's name.
  When an assertion right before it claims the same thing, use `SurgeryDriver.AssertAndCapture(holds, claim,
  keyFrame)` so the text is written once.
- Review the frames for continuity, clipping, mesh intersections, material consistency, tool contact, animation
  transitions and UI legibility. Screenshot comparisons may flag regressions but don't replace that review.
- `tests/KeyFrames` is the committed baseline the review compares against: JPEGs of the key frames of the last
  reviewed full regression. It is updated only by `./build.py generate_baseline`, which leaves it alone after a focused
  run, and only after every sheet the report lists looks right.
- Rerun flaky tests individually and use the successful run as the new baseline: the full regression does this itself
  (above). Allow failure in the general baseline update flow. However review the failures manually and update the
  baseline only if the case is not visibly broken: open the sheets of every suite that still failed, and fix it first
  when one shows a defect.
- Never commit key frames of a focused run, of a case marked broken, or ones that show a defect; never edit the folder
  by hand. A change with no missing, changed or new key frames leaves it untouched.
- Key frames are taken and compared in local runs only, never on CI.
  They are always rendered in a virtual display by the software renderer (`xvfb-run`), without film grain, so machines
  save the same or nearly the same pixels for the same scene.
  The review errs toward listing a key frame: a faint change over the whole view counts, so a sheet may show no
  visible difference.

## Frame-time budget

- Gameplay stays within a 16 ms worst frame so 60 fps remains possible. Displayed FPS isn't the metric.
- Two checks, one call: tests that exercise dynamic work check it with `Budget.Check()` (`tests/Support/FrameBudget.cs`),
  never with a timer around one function. A case known to go over that can't be fixed in the current change passes
  its reason as `broken`.
  - CPU budget, every local run: rendering off (`FrameBudget.RenderingOff()`), the game's own work per frame within
    8 ms on the reference machine (an i9-14900HX), scaled by how much slower this machine runs a fixed benchmark.
    It holds on any machine, with or without a GPU.
  - Render budget, `./build.py full_performance_run` only: rendering on, whole frames within 16 ms on the real GPU.
- Frame times are checked only in suites that run alone (`--jobs 1`, the default, or with key frames). CI passes
  `--ci-run`, which doesn't check them.

## Gotchas

- Godot exports .NET projects through `ThisScalpelIsMine.sln`: keep it next to the `.csproj`.
- Exported games compile without `tests/` and the GdUnit4 packages: game code must not rely on anything only they
  bring, such as the test project's global usings.
- A C# class Godot attaches to a node must be `partial`, derive from a Godot class and live in a file named after it.
  Rebuild (`./build.py setup`, or any `./build.py test`) before Godot can find a new one.
- GDScript habits that bite in C#: a `for` condition is evaluated every iteration, and float math is single precision
  (round in double where a boundary matters).
- `FindChildren(pattern, type)` only matches engine classes; for C# classes use
  `FindChildren("*", "", true, false).OfType<T>()`.
- `./build.py assets` rewrites many `.glb` files with byte-only differences. Commit only the models you meant to change.
- Manual pages write game numbers as `{expression}` with C# names, never by hand (see Data formats in DESIGN.md).
  Give a number the manual needs a named constant first.
- Generator colors are display (sRGB) values, converted to linear when written to glTF. Pick them like any color picker.
